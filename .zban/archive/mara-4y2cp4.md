## Decisions made

- `Status` counts as a field value of REQ-UPDATE-ITEM; `Type`, `ID`, the MID and relations do not (VER-UPDATE-ITEM). Otherwise no operation could change a status, and the epic's agent could not accept items without hand edits.
- A refused `project init` creates nothing (VER-PROJECT-INIT). This reads its refusal together with REQ-REFUSED-EDIT-CHANGES-NOTHING and follows 0.3.0, which rejected an existing project.
- The write-safety items cover `project convert` as well as the item, relation and fix operations, since nothing limits "edit" to authoring. `project init` is covered only by VER-REFUSED-EDITS, since it writes no items or links. Rejected: leaving the converter out, which would narrow REQ-INTERRUPTED-EDIT-LOSES-NOTHING without saying so.
- VER-FIX-CASES checks "malformed item formatting" on `missing-separator`, an anchor that lacks only its blank line, and a setext heading in an item's heading place, where the repair is unambiguous. mara-pvqpse may repair more.
- Work counters of writes: the checks of DES-WRITE-PROCEDURE re-read a file only when DES-INPUTS-AND-KEYS would. Counts are pinned for files last changed at least 2 s earlier. `prime` and `project init` read nothing. The warm rows count one parse per distinct content written that no file of the session had, and none for a file given another input's contents (review round 1).
- Hub write cases (rename, move, fix) gate per-link quadratic work, which the generated corpus's bounded fan-in cannot show.
- Interruptions (review rounds 1 to 3): `RLIMIT_FSIZE` below the new size of a padded file F kills the process while it writes F's temporary file (`SIGXFSZ` at its default) or fails that write with `EFBIG` (`SIGXFSZ` ignored). The debug-build pause point (below) stops the writer before F's second check, where the test changes F or removes write permission from F's directory. For the first or only file, VER-REFUSED-EDITS has a change before that file's pause point (refused, or applied to the new contents) and one during it (refused, nothing replaced).
- A case that needs a later slice names it: code markers in alpha.5 (mara-yhxq5x), the daemon in alpha.4 (mara-0mxw21), Node in alpha.6 (mara-xzfeyj), `query` parity in alpha.3 (mara-bx82k0), and the engineering programs in alpha.3 (mara-tx0fcf).
- The pass criteria leave open what the docs leave open. That includes a create without a body, clearing an optional field, a duplicate relation row or a cycle from `relation add`, a move into a new document, slugs of non-ASCII titles, whether `project init` creates a missing named directory, and whether a bound MCP server rejects a per-call project.
- Decided by the maintainer: the converter writes the documents first and the configuration last. An interrupted conversion leaves a 0.3.0 project that every other operation refuses with `legacy-project` and that a rerun completes, and REQ-INTERRUPTED-EDIT-LOSES-NOTHING now lists that leftover (DES-CONVERSION-MAPPING, ADR-CONVERSION-RERUN, VER-INTERRUPTED-EDITS, VER-CONVERSION). Chosen option: "Config last, rerun completes (Recommended) — The converter writes the documents first and the configuration last. An interrupted run leaves a 0.3.0 project that every other operation refuses with `legacy-project` and that rerunning the conversion completes. "A 0.3.0 project that rerunning the conversion completes" is added to the allowed leftovers. No user data is lost; the requirement's list grows by one entry."
- Decided by the maintainer: `project convert` has no scaling case. Its counter rows are asserted through the real CLI on a small hand-written 0.3.0 fixture, not on generator output (REQ-NEAR-LINEAR-SCALING, VER-SCALING, VER-WORK-COUNTERS, DES-PERFORMANCE-HARNESS, ADR-NO-CONVERTER-SCALING). Chosen option, not the one recommended: "Exempt the converter — `project convert` gets counter tests on a small fixed input and no scaling test. Loosens REQ-NEAR-LINEAR-SCALING for one operation that each user runs once."
- Decided by the maintainer (review round 2): before writing any document, the converter writes the whole report to `.mara/conversion-report.json` (`format_version` 1, entries of path, line and message). The file stays as the record; a rerun keeps the entries of documents already converted, computes the rest, and returns the whole report; an unreadable report file refuses the conversion (DES-CONVERSION-MAPPING, DES-INPUTS-AND-KEYS, ADR-CONVERSION-REPORT-FILE, VER-CONVERSION, VER-INTERRUPTED-EDITS, VER-WORK-COUNTERS). Question: "`mara project convert` must report whatever it leaves out (REQ-CONVERT-DIRECTIVE-CORPUS, Accepted). If it is killed halfway, the documents already converted have lost their 0.3.0 text, so a rerun cannot report again what was dropped from them (symmetric relation rows, relations to non-item targets, inline typed relations). With `--format json` or MCP the report only comes with the final result, so a killed run delivers nothing. How should the report survive an interruption?" Chosen option: "Report file in the project (Recommended) — Before writing any document, the converter writes the whole report to a file in the project, for example `.mara/conversion-report.json` with its own format version. It stays as a record of the conversion. A rerun keeps the entries of documents already converted and returns the whole report. Complete on every surface and survives a power loss; adds one persisted file to every converted project." Rejected: printing the report before the first write, and keeping the dropped text in the converted document as an HTML comment.
- Report entries on a rerun (review round 4): a rerun keeps every entry already in the report file and adds each computed entry it does not hold with the same path, line and message. No recorded entry is dropped, also for a converted document that gained 0.3.0 syntax by hand; an entry whose line no longer matches stays beside the rerun's entry at the new line. Rejected: recomputing the entries of documents that hold 0.3.0 syntax again, which dropped the omissions of such a hand-edited converted document.
- Decided by the maintainer (review round 3), replacing the rejected "fault-injection hook" entry: one pause point before each file's second check, compiled only into debug builds; `MARA_TEST_PAUSE` names a directory where the writer creates `paused` with the file's path and waits until the test removes it; a release-build `performance` case checks that no trace of it remains (DES-WRITE-PROCEDURE, ADR-DEBUG-PAUSE-POINT, VER-REFUSED-EDITS, VER-INTERRUPTED-EDITS, mara-6ex559). Question: "The interruption tests in VER-INTERRUPTED-EDITS have now drawn a defect in three review rounds, always on the same point: proving through the real CLI that the writer re-checks a file's hash just before renaming it (write procedure step 3). From outside the process there is no event between the first check and the second, so every black-box trigger tried so far was either a race or excluded a valid implementation. How should this check be verified?" Chosen option: "Pause point in debug builds (Recommended) — The writer gets one pause point before each file's second check, compiled only into debug builds (the tests run the debug binary; the release binary has no trace of it). A test tells it to wait, changes the file, and lets it continue. Deterministic on a busy machine and a few lines of code, but it is test-only code in the writer, which AGENTS.md wants you to approve." Rejected: no hook, with the mechanism left to the writer issue (a race that must be retried and may flake under load); a unit test below the CLI (departs from "tests run the real CLI" and needs a seam in the write function).
- Decided by the maintainer (review round 4): the same debug-only mechanism also pauses once per edit, after the edit is computed and before the step-2 check, signalled by an empty `paused`; VER-REFUSED-EDITS changes the only, first or a later target there and requires a refusal with nothing replaced, which replaces the earlier two-outcome row (DES-WRITE-PROCEDURE, ADR-DEBUG-PAUSE-POINT, VER-REFUSED-EDITS, mara-6ex559). Question: "[…] Step 2 of the write procedure checks every file an edit will write before anything is written, so a stale edit is refused whole. The pause point you approved sits before each file's second check (step 3), so no test can change a later file after it was read and before step 2. A writer that skips step 2 would pass: it would replace the first file and only then notice the later one changed, leaving an interrupted edit where a refusal is required. How should step 2 be verified for later files?" Chosen option: "Second pause location (Recommended) — The same debug-only mechanism also pauses once per edit, after the edit is computed and before the step-2 check. A test changes a later file there and expects a refusal with nothing replaced. Deterministic; extends your pause-point decision from one location to two, still debug builds only and no general fault-injection facility." Rejected: verifying step 2 by inspection (a regression that drops step 2 would fail no test); accepting either a refusal or an interrupted edit (REQ-REFUSED-EDIT-CHANGES-NOTHING then not shown for multi-file edits).
- Decided by the maintainer, replacing my decision that a direct CLI call may skip re-derivation: step 4 of DES-WRITE-PROCEDURE binds only hosts that keep state, and a direct CLI call does no read, hash, parse or snapshot build after the renames. The cold write row of VER-WORK-COUNTERS asserts exactly that (DES-WRITE-PROCEDURE, ADR-NO-REDERIVATION-IN-CLI). Chosen option: "CLI re-derives nothing (Recommended) — Step 4 is a bound for hosts that keep state (the daemon re-derives only the changed files, never the whole project). A direct CLI call does no read, hash, parse or snapshot build after the renames, and the counter row asserts exactly that. Fastest; the edit was already computed and checked before writing."
- Decided by the maintainer: a rename rewrites code markers and mention text, then the `ID` row, then inbound relation link text (DES-WRITE-PROCEDURE, ADR-MENTIONS-BEFORE-ID-ROW, VER-INTERRUPTED-EDITS, VER-RENAME-ID; closes mara-8y9zsb). Chosen option: "Mentions before the ID row (Recommended) — Order becomes: code markers and mention text, then the `ID` row, then inbound relation link text. A rename stopped before the `ID` row is completed by a rerun; one stopped after it leaves only stale relation link text, which is reported and which fix rewrites. No stale mention can remain unnoticed. Changes the Accepted order by one step."

## Rejected approaches

- Triggering on a temporary file's name or growth (review round 2): a writer that writes an unnamed `O_TMPFILE` gives no such event before its check, so a conforming writer could not be stopped there.
- Repeating the `project fix` recovery case in VER-INTERRUPTED-EDITS: it would need two parallel issues, mara-esxqzv and mara-pvqpse. VER-FIX-CASES holds it instead, on stale links in several files.
