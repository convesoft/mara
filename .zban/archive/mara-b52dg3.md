## Summary of Changes

- Engine (`crates/mara-engine`, no I/O, builds for `wasm32-unknown-unknown`): `diagnostic` (DES-DIAGNOSTICS fields and its CLI line form), `config` (`parse_config`, `CONFIG_PATH`, `LEGACY_CONFIG_PATH`, `Root::recognize`), `schema` (`parse_schema` into types, fields, statuses and relations with per-source targets, `same_type`, `acyclic`) and a private TOML reader that locates every problem by line. Contents arrive as bytes, so UTF-8 decoding is the same on every host. New dependency: `toml` 1.1.8 with only `std` and `parse` (spanned tables, no serde).
- Host (`crates/mara/src/lib.rs`, `project.rs`): `select` (ancestor search or `--project`, canonical roots, 0.3.0 refusal naming `mara project convert`), `recognize` (for the input inventory of mara-8d6cnw to skip nested roots) and `load` (reads the configuration and the schema it names, returns both, as far as valid, with every diagnostic). `main.rs` is unchanged; `mara` now depends on `mara-engine`.
- Docs: DES-PROJECT-CONFIGURATION gains the selection rule, required settings, path form, format-version and partial-loading rules and the table of codes; DES-SCHEMA-MODEL gains the schema keys, defaults, name and ID-prefix forms, reserved and distinct names, target rules and partial loading, with `repeatable`, `same_type` and `acyclic` in its example.
- mara-000f9q and mara-bmc9gc name the real-CLI cases that only host tests cover now. Filed mara-2659w3 (count these reads, blocked by mara-csmk0c) and mara-zv9d69 (decision on operations other than validation).

Review fixes (second commit): `load` refuses a schema whose real path lies outside the project or in a nested or 0.3.0 project (`outside-project`); a declaration with one invalid part still has its other parts checked; the DES-SCHEMA-MODEL example is self-contained and both documented examples are loaded by the engine tests straight from docs/project.mara.md; every decision below has its sentence in DES-PROJECT-CONFIGURATION or DES-SCHEMA-MODEL.

Rebased onto the harness (mara-csmk0c): a corpus test in crates/mara/tests/performance/corpus.rs loads a generated 1× project through `select` and `load` and requires no diagnostics. The harness schema loaded cleanly as it landed; it now also carries the `repeatable`, `same_type` and `acyclic` flags of DES-ENGINEERING-VOCABULARY, which DES-SCHEMA-MODEL did not define when it was written.

Decided by the maintainer on 2026-11-14 (mara-3s1kpq), option A, chosen as "A: no symlinks (Recommended)": "One more round by the same worker. Mara follows no symbolic link when it reads .mara, .mara/config.toml or any component of the schema path: such a path is refused with a diagnostic. Schema names are collected before declarations are validated; further hidden-error combinations found later become follow-up issues. Cost: no symlinked configuration or schema at all."

Third round (after the second review): `load` walks `.mara/config.toml` and the schema path as written with `symlink_metadata` and refuses the first symbolic link (`symbolic-link`) and any component that is another project's root (`outside-project`), replacing the canonical-path check; `recognize`, and so the ancestor search and `--project`, refuses a `.mara` that is a symbolic link. The schema reader collects relation, inverse and field names from the tables as written before it validates any declaration. The documented examples moved from the engine to a host test, so the packaged engine has no file outside its crate. DES-PROJECT-CONFIGURATION states the symlink rule and the maintainer's answer to mara-zv9d69.

Decided by the maintainer on 2026-11-14, on whether a process that rewrites the project during a load is within the rule's scope, option A, chosen as "A: out of scope (Recommended)": "The rule is checked on the path as it is when Mara reads it. A process that can swap files in the project during a load can already write any schema it wants, so the race gives it nothing new. The limit is written into DES-PROJECT-CONFIGURATION; no code change. The branch gets one small last fix (below) and a re-check limited to that." DES-PROJECT-CONFIGURATION states the limit next to the symbolic-link rule; the code is unchanged for it.

Fourth round (after the third review): `statuses`, field `values` and each source's target list track their entries as written, apart from the entries kept, so a repeated entry is reported at its later occurrence even when it is also invalid or names an undeclared type (DES-SCHEMA-MODEL).

## Decisions made

- No real-CLI surface in this issue. The documented operations that would show loading are `project validate`, `schema validate` (mara-000f9q) and `schema list`/`schema get` (mara-bmc9gc); each has a paged result, JSON output and work-counter tests that belong to its issue. The behaviour is tested through the host API on real disposable projects, and those issues now list the real-CLI cases. Rejected: implementing `schema validate` here, which would split one operation across two issues and fix its result format before mara-000f9q.
- Selection stops at the nearest directory whose `.mara/` holds an entry named `config.toml` or `project.toml`, so a nested 0.3.0 project is refused rather than skipped; `--project` names the root itself, relative to the working directory, and is not searched from; a stat error other than not-found stops the search (`io-error`) so another project is never chosen in its place. Roots are canonical. (DES-PROJECT-CONFIGURATION)
- Every setting of the v1 example is required; settings for programs, code languages and consumers are unknown until their slices add them. Paths and patterns are relative, `/`-separated, without empty, `.` or `..` parts; glob syntax is left to the inventory. (DES-PROJECT-CONFIGURATION)
- A `format_version` other than 1 stops reading its file, or leaves every document unread for `[documents]`; a missing one is reported and the file read as 1. Every other problem leaves out only what it concerns, so validation can report every problem (VER-SEEDED-PROBLEMS). (DES-PROJECT-CONFIGURATION, DES-SCHEMA-MODEL)
- Codes: `no-project`, `not-a-project`, `legacy-project`, `io-error`, `toml-syntax`, `unsupported-format-version`, `unknown-key`, `missing-key`, `invalid-value`, `duplicate-name`, `undeclared-type`, `reserved-name`. A schema that cannot be read is reported at the configuration line naming it. (DES-PROJECT-CONFIGURATION)
- Schema keys: `statuses`; `types.<name>` `id_prefix`, `description`, `fields`; `fields.<name>` `kind`, `values`, `required`, `repeatable`; `relations.<name>` `inverse`, `description`, `targets`, `same_type`, `acyclic`. Flags default to `false`; `types`, `relations` and `fields` are optional; the rest is required. (DES-SCHEMA-MODEL)
- Names are lowercase ASCII letters and digits in parts joined by single `_` or `-`, so labels never collide and never end in a space; ID prefixes are uppercase parts each ending with `-` (DES-ITEM-IDS). `type`, `id` and `status` are reserved for fields and relations; forward and inverse names are all distinct (an inverse equal to its forward name would be the dropped symmetric relation); a field may not share its name with a relation its type is a source of; `code` is never a target; `same_type` admits only the source's own type and no `code` source. (DES-SCHEMA-MODEL)
- Name collisions are found from the names as written (maintainer's decision) and reported at the later occurrence in the file: of a relation name and an inverse name, of two inverse names, and of a field and a relation name its type is a source of, whichever is declared later. What is left out does not depend on the order: an inverse name that repeats a relation name or an earlier inverse name, and the field of a field/relation pair. (DES-SCHEMA-MODEL)
- A symbolic link at `.mara`, `.mara/config.toml` or a schema path component has its own code, `symbolic-link`, distinct from `outside-project` (now only a schema path that enters another project's root, 0.3.0 roots included). The ancestor search and `--project` refuse a `.mara` that is a symbolic link with `symbolic-link` instead of following or skipping it, so another project is never chosen in its place; so does the nested-root check along the schema path. A missing component ends the walk and the read reports `io-error`. Include patterns are not read by `load`; the inventory applies the nested-project rule to them, and must handle the `symbolic-link` error that `recognize` returns. Overturned: my second-round rule (canonical path inside the project, a symlink staying inside loads). (DES-PROJECT-CONFIGURATION)
- A missing `format_version` is an error (the Accepted item says each file carries one); the rest of the file or table is still checked as version 1 so that its other problems are reported. Until 0.4.0, a setting the binary does not implement yet is unknown, and adding it keeps `format_version` 1. The project root is canonical. (DES-PROJECT-CONFIGURATION)
- A declaration with an invalid name or part is checked in full before it is left out, so one problem never hides an independent one. A description is not empty; statuses, enum values and each source's targets list at least one name, none twice; `targets` names at least one source. (DES-SCHEMA-MODEL)
- Both TOML examples on docs/project.mara.md are complete. A host test in crates/mara/tests/project.rs reads them with `include_str!` from the page, each located as the first TOML block after its item's ID row, writes them as one project and requires `select` and `load` to report no diagnostics. Rejected: copies in the tests, which drift; tests in the engine crate, whose package does not hold `docs/` (the `mara` crate cannot be packaged: its `mara-engine` dependency has no version). (DES-PROJECT-CONFIGURATION, DES-SCHEMA-MODEL)
- The first decision above is work scheduling, recorded in mara-000f9q and mara-bmc9gc rather than in a Mara item; every other decision has its sentence in the item named after it.
