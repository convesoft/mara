## Decisions made

- The engine hashes (`mara_engine::hash`), so every host derives the same keys; the host decides when, by stat. Rejected: hashing in the host only, which would let hosts disagree on keys that cursors carry. (DES-INPUTS-AND-KEYS)
- One request has one `now`; `Inputs::project` loads once per `now`, so a request that loads and then builds reads nothing twice, even for files changed in the last 2 s.
- A file read in one request under one role is shared with its other roles in that request: the configuration and the schema join a per-request set of reads, which the schema, `.gitignore` files and documents consult before reading, so a schema that is also a document, the configuration or a `.gitignore` is read and hashed once (review finding 7). Only project files join the set, so documents are not held twice. (DES-INPUTS-AND-KEYS)
- The inventory lists only the root and the directories in which a pattern can still match; the `.gitignore` files of those directories are the inputs, and no other `.gitignore` is read. An entry named `.git` is skipped at any depth. A document is a listed `*.mara.md` file a pattern matches (DES-REGIONS). (DES-INPUTS-AND-KEYS)
- `.gitignore` files are matched by the `ignore` crate (as decided by the maintainer, below), fed the lines of the bytes Mara read and counted, as the crate's own reader splits them: a leading UTF-8 byte order mark skipped, a CR before each LF removed, comment lines skipped before anything else. The crate takes a pattern only as text, so a line that is not UTF-8 is never decoded lossily: the file cannot be applied. The crate refuses a bad pattern line by line (`add_line`) and a pattern set it cannot compile as a whole (`build`, such as `error building NFA`); either makes the file one that cannot be applied, reported with the crate's reason at that line, or line 1 for the whole set, and a partly built matcher is never used. A refused file is tracked like a compiled one, so an unchanged one is not read again and is still reported. Code `unsupported-gitignore`, in the style of `unsupported-format-version`. Rejected: `io-error`, since the file was read. Its known limitation, observed with ignore 0.4.34 against Git 2.56 and pinned by one test each: `{a,b}` alternates, `[[:digit:]]` is a set followed by `]`, trailing tabs are trimmed, and a NUL byte stays in the pattern; Git reads all four differently. (DES-INPUTS-AND-KEYS)
- A `.gitignore` that cannot be applied is an error at its path, and nothing in its directory or below is an input, since any entry there might be one it ignores: one that is unreadable, not a regular file or a symbolic link (`io-error` or `symbolic-link`, line 1), or one the `ignore` crate cannot take (`unsupported-gitignore`, previous entry). It is never opened unless the listing shows a regular file, and never applied in part. Rejected: applying no patterns from it, which makes ignored files inputs, the opposite of DES-INPUTS-AND-KEYS. (DES-INPUTS-AND-KEYS)
- Symbolic links (decision 2 of the brief, under the worker rules): the inventory follows none, not even to stat its target. A link a pattern matches as a document is `symbolic-link` at the link's path, line 1, and is not read; a `.gitignore` that is a link follows the rule for a `.gitignore` that cannot be applied. Any other link is skipped like an undeclared file, so nothing below a linked directory is an input. A directory whose `.mara` is a link (the `recognize` error) is `symbolic-link` at that `.mara`, and nothing below the directory is an input: neither followed nor silently skipped, as for selection. Rejected: reporting every link, which would report links no pattern declares, such as this repository's `CLAUDE.md`; reporting linked directories below which a pattern could match, which cannot tell a linked file from a linked directory without following the link. No link lets an operation read a file of another project or outside the root. (DES-INPUTS-AND-KEYS, `symbolic-link` row of DES-PROJECT-CONFIGURATION)
- A directory that cannot be listed or examined for a `.mara`, an input that cannot be read or is not a regular file, and a name that is not UTF-8 where an input could be are `io-error` at that path, line 1; nothing below is an input and the inventory goes on. These diagnostics come with each `Generation`, not in the snapshot, since they do not follow from its key. `load` now stats before it reads, so a configuration or schema that is a directory or a pipe is `io-error` instead of a read that fails or blocks. (DES-INPUTS-AND-KEYS)
- `PARSER_VERSION` versions everything `parse` derives, search words included. The snapshot key hashes a kind name, `SNAPSHOT_VERSION` (1), the configuration hash and the schema hash (each marked absent when the file was not read), then each document's path, parser version and file hash in path byte order. (DES-INPUTS-AND-KEYS)
- Edges: a row keyed by a relation the schema declares whose value is a link with a MID fragment, whatever the item's type (validation judges the endpoints), and every mention, in items and in the narrative. Inverse edges are kept by target MID, so a missing or repeated target costs nothing extra. Without a readable schema there are no relation edges. The ID map holds every `ID` row; the MID and ID maps keep every item of a repeated key. (DES-SNAPSHOT)
- Search words: maximal runs of letters and digits, lowercased (`document::words`, also for queries), from an item's MID and `ID` values, title, other metadata values and body text, each as GitHub shows it, with its zone. All of it comes from the parser's one event pass: metadata values from each cell's text events (new `Row::text`), so a link inside other text gives its text and never its destination (review finding 4); the title from the heading block. Block, table-cell and line boundaries, a nested rule and every inline HTML tag end a word, while emphasis, strikethrough, links, images and code spans do not (review finding 3); an image gives its alt text, an autolink its address, which is its text. Rejected: keeping inline HTML continuous, since `a<br>b` shows two words. The parser derives the words per document, so text is normalized once per file change, and the build merges them. Narrative text is not indexed: narrative units come with mara-bmc9gc, which extends the same pass. (DES-SNAPSHOT)
- Broken projects: `Inputs::snapshot` always builds, so validation reports on a project whose configuration or schema has errors; an operation that must refuse calls `Inputs::project` first and checks `Project::has_errors`. (DES-PROJECT-CONFIGURATION)
- Tests below the CLI live in the `performance` target next to the CLI cases, and the scaling test times a cold build with the same rounds and limit. (DES-PERFORMANCE-HARNESS)

The second commit replaced the crate with an own matcher; the maintainer then decided to keep the crate (below), so the third commit restored it and fixed the two calls: such a file is now reported as `unsupported-gitignore` and nothing below it is an input (the two `.gitignore` decisions above). Tests: `a_gitignore_the_crate_cannot_compile_keeps_its_directory_out` (the review's 300,000-character pattern at line 1, and `[z-a]` refused at line 2) and `a_gitignore_line_that_is_not_utf8_keeps_its_directory_out` (the review's bytes), each naming what Git does; `gitignore_files_filter_as_in_git` and `gitignore_escapes_and_double_stars_filter_as_in_git` against Git for patterns the crate reads as Git does; and one `known_limitation_*` test per difference, which pins the crate's behaviour and Git's (crates/mara/tests/inputs.rs).
- 3, 4: search words ran blocks together and indexed link destinations in mixed metadata text. Fixed in the parser's event pass (the search-words decision above). Tests: `every_block_boundary_separates_words` and `no_destination_or_html_is_indexed` (crates/mara-engine/src/document/tests.rs).
- 5: a `.gitignore` that is a pipe was silently skipped. It is now `io-error` without being opened, under the rule for a `.gitignore` that cannot be applied, as are a directory, an unreadable file and a link. Test: `a_gitignore_that_cannot_be_applied_keeps_its_directory_out`.
- 7: a schema that is also a document was read and hashed twice. Fixed by sharing the request's reads (decision above). Test: `a_file_with_two_roles_is_read_once_per_request`, which also covers a schema that is the configuration or a `.gitignore`. A `.gitignore` or the configuration can never be a document, since documents are `*.mara.md`.

Re-check of 087a02a, fourth commit: an HTML tag in a metadata value still ran words together, because a boundary reached the block's text but not the open cell's; both get it now. `every_boundary_separates_words_in_every_place` runs each boundary of DES-SNAPSHOT in the title, a metadata value and the body, wherever Markdown can put it there, and `an_html_tag_in_a_metadata_value_separates_words` is the reproduction. `Row::text` reads each run of spaces as one. The codes table of DES-PROJECT-CONFIGURATION now says which codes selection, loading and the inventory report, with the inventory's uses of `io-error` and `symbolic-link` and the new `unsupported-gitignore`.

The other three confirmed behaviour the maintainer decided (below). Checks: the six local checks of AGENTS.md exit 0 on a clean tree at the final head.

## Decided by the maintainer

On the include-pattern syntax (finding 6), chosen over keeping 0.3.0's globs:

> B: reduced syntax — Keep the worker's syntax: `**` as a whole path part, `*` and `?` within a part, everything else literal, so no pattern is ever invalid. A dropped capability: the converter must flag 0.3.0 patterns that use braces or classes, and the docs state the change.

Carried out: DES-PROJECT-CONFIGURATION states the syntax and that braces and character classes, pattern syntax in 0.3.0, are none in 0.4.0, where `{`, `}`, `[` and `]` match themselves. DES-CONVERSION-MAPPING (docs/migration.mara.md) maps such a pattern to itself, reported, and the dropped-capabilities table lists it. mara-wjy3sh has the obligation and a fixture. No Verification item covers the converter's configuration handling. The matcher is unchanged.

On the 2 s rule (finding 8), chosen over the row as written:

> A: worker's rule, amend row (Recommended) — Keep the worker's rule and amend the warm row: 0 hashes when every input was last hashed at least 2 s after its modification; otherwise one extra hash for that input, no parse, no build. This catches an edit made in the same timestamp tick as the previous hash, which the row's literal reading misses on coarse-timestamp filesystems.

Carried out: DES-INPUTS-AND-KEYS states the rule once (a re-hash when the check that last hashed a file came less than 2 s after its mtime or ctime), and the two warm rows of VER-WORK-COUNTERS use the same terms and link to it. mara-p27z9t names no row text, so it is unchanged. Tests: `an_input_hashed_within_2_s_of_its_change_is_hashed_once_more` (the review's reproduction, with the clock injected rather than waited for), `a_check_that_began_before_a_change_is_repeated_once`, and `an_edit_in_the_tick_of_the_hashing_check_is_found_later` (crates/mara/src/tracked.rs). The rule is unchanged.

On shared parses (finding 9), chosen over parsing per path:

> A: per content, amend row (Recommended) — Parses are counted per distinct document content. The cold row becomes "1 parse per distinct document content" and gains a duplicate-content case. A moved or copied document costs no parse; paths, diagnostics and spans stay per file.

Carried out: the cold row of VER-WORK-COUNTERS reads "1 parse per distinct document content" and includes two documents with the same contents; DES-INPUTS-AND-KEYS adds that paths, diagnostics and spans stay per file. mara-000f9q and mara-bmc9gc name the case in their cold-row items. Test: `identical_documents_are_parsed_once_and_kept_per_path`. The sharing is unchanged.

On how `.gitignore` files are matched, after the orchestrator raised that the second commit's matcher was described as a port of Git's `dir.c` and `wildmatch.c` (Git is GPL-2.0, Mara MIT/Apache-2.0), chosen over keeping an own matcher (with clean provenance, or as it is):

> B: back to the crate (Recommended) — Return to the `ignore` crate (MIT/Unlicense, from ripgrep) and fix only the two calling mistakes: pass bytes, and report a .gitignore the crate cannot compile, treating nothing below that directory as an input. The crate's three differences from Git (brace alternation, POSIX classes like [[:digit:]], trailing tabs) are written into DES-INPUTS-AND-KEYS as a known limitation. No licence question, much less code to own.

Carried out in a third commit: `crates/mara-engine/src/gitignore.rs`, its module, its tests and every use are gone, and `ignore` 0.4.34 is back in the host crate. The two calls are fixed as described in the `.gitignore` decisions above. DES-INPUTS-AND-KEYS states the known limitation beside the Accepted sentence, which is unchanged, and adds the crate's refusals to the rule for a `.gitignore` that cannot be applied. Verifying the three differences against Git found a fourth that behaves the same way: a NUL byte stays in the crate's pattern, while Git ends the pattern there. It is written into the same limitation and pinned by its own test.
